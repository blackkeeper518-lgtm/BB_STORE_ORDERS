# BLACKBOX ALERT CENTER

## ศูนย์ป้ายเตือนของ BB STORE

> **เอกสารนี้ว่าด้วย “ส่วนห้องเตือน” โดยตรงเท่านั้น**
ไม่ใช่เอกสารรื้อระบบ Order Control, Telegram Room หรือ BLACKBOX Room และไม่สั่งให้ย้ายหน้าที่ของห้องเหล่านั้น

---

## 1. สรุปสั้นที่สุด

**BLACKBOX ALERT CENTER** คือหน้ากลางที่รับสัญญาณผิดปกติจากระบบ แล้วบอกคนทำงานว่า:

```
เกิดอะไรขึ้น
→ รุนแรงแค่ไหน
→ ต้องทำอะไรต่อ
→ ต้องไปห้องไหน
```

มันไม่ใช่ห้องที่เอาออเดอร์มาทำซ้ำทุกอย่าง และไม่ใช่ห้องที่ตัดสินแทนคนว่ารายการไหนจริงหรือปลอม

> **หน้าที่ของศูนย์ป้ายเตือนคือ “เห็นก่อน ชี้ถูกห้อง และไม่ทำให้ออเดอร์หลุด”**

---

## 2. จำนวนห้องที่ล็อกไว้

ในภาพรวมของระบบมี **4 ห้อง** โดยส่วนที่เรากำลังทำโดยตรงคือห้องแรก

| ลำดับ | ชื่อห้อง | สถานะในงานนี้ | หน้าที่หลัก |
| --- | --- | --- | --- |
| 1 | **BLACKBOX ALERT CENTER** | **ห้องที่กำลังทำโดยตรง** | รวมป้ายเตือนและชี้ทางไปห้องที่ต้องจัดการ |
| 2 | **ORDER CONTROL** | ห้องปลายทาง | ลงมือแก้ไขและจัดการออเดอร์หลัก |
| 3 | **BLACKBOX ROOM** | ห้องปลายทาง | แกะรอยว่าเหตุการณ์ซ้ำหรือผิดปกติเพราะอะไร |
| 4 | **TELEGRAM ROOM** | ห้องปลายทาง | คุมคิวและสถานะการส่งออเดอร์ |

### หลักแบ่งงาน

- **Alert Center เห็นเหตุการณ์ก่อน**

- **Order Control ลงมือกับข้อมูลออเดอร์**

- **BLACKBOX Room สืบเหตุผลและหลักฐาน**

- **Telegram Room คุมการส่งออก**

เอกสารนี้กำหนดเฉพาะ **ศูนย์ป้ายเตือนและเส้นทางส่งต่อ** ไม่ได้รวมงานพัฒนารายละเอียดภายในสามห้องปลายทาง

---

## 3. งานของ BLACKBOX ALERT CENTER

### ต้องทำ

- รับสัญญาณจาก n8n, Order Control, BLACKBOX Room และ Telegram Room

- สร้างป้ายเตือนที่คนอ่านแล้วเข้าใจทันที

- แยกความเร่งด่วนเป็นระดับ

- บอกเหตุผลที่เตือนพร้อมหลักฐานสั้นๆ

- บอกปลายทางว่าต้องไปห้องไหน

- ให้กดเปิดเคส/เปิดห้องปลายทางได้

- เก็บป้ายที่ปิดแล้วไว้ย้อนดู

- แสดงระบบกำลังเฝ้าอะไร แม้ไม่มีภัยร้อน

### ห้ามทำ

- ห้ามลบข้อมูลที่ n8n ส่งมา

- ห้ามเขียนทับหลักฐานเดิม

- ห้ามตัดสินอัตโนมัติว่าแถวไหนเป็นออเดอร์จริง

- ห้ามให้ Alert Center กลายเป็นหน้าจัดการออเดอร์ซ้ำกับ Order Control

- ห้ามให้ป้ายเตือนมีแค่คำว่า “ซ้ำ” โดยไม่บอกว่าซ้ำเพราะอะไร

- ห้ามส่งของต่อโดยอัตโนมัติเพียงเพราะป้ายถูกปิด

## 4. คอลัมน์หน้าเว็บของ Alert Center

หน้าเว็บหลักควรมีตารางกลางชื่อ **ALERT BOARD · กระดานป้ายเตือน**

### คอลัมน์ที่ต้องมี

| ลำดับ | ชื่อคอลัมน์บนหน้าเว็บ | ใช้ดูอะไร |
| --- | --- | --- |
| 1 | **ป้าย / ระดับ** | ป้ายนี้ร้อนแค่ไหน: กั้น, ต้องดู, หรือเฝ้า |
| 2 | **เกิดอะไรขึ้น** | สรุปเหตุการณ์ด้วยภาษาคน เช่น “โฟร์ยิงซ้ำ” |
| 3 | **เพจ / ลูกค้า / Order** | ระบุต้นทาง คนที่เกี่ยวข้อง และเลขออเดอร์ |
| 4 | **วันที่ · เวลา** | เวลาที่เหตุการณ์เกิดหรือเวลาที่ระบบพบ |
| 5 | **สินค้า / ยอด** | สินค้า จำนวน และ COD ที่เกี่ยวข้อง |
| 6 | **หลักฐานสั้น** | ข้อความ แหล่งที่มา หรือสัญญาณที่ทำให้ระบบเตือน |
| 7 | **เหตุผลที่เตือน** | อธิบายว่าซ้ำเพราะอะไรหรือผิดปกติตรงไหน |
| 8 | **ต้องทำอะไร** | คำสั่งถัดไป เช่น กั้นก่อนส่ง, เทียบแชท, ตรวจข้อมูล |
| 9 | **ไปห้องไหน** | ปลายทางชัดเจน: Order Control, BLACKBOX Room หรือ Telegram Room |
| 10 | **สถานะป้าย** | ใหม่, กำลังตรวจ, รอคนตัดสิน, ส่งต่อแล้ว, ปิดแล้ว |
| 11 | **รอยมือ** | ใครกดอะไรและกดเมื่อไหร่ |

### คอลัมน์ที่ควรแสดงเป็นพิเศษเมื่อเป็น “เปลี่ยนสินค้า”

ถ้าป้ายเกี่ยวกับการเปลี่ยนสินค้า ให้แสดงเพิ่มในคอลัมน์สินค้า/หลักฐาน:

```
รอบแรก: สินค้า A · 2 ชิ้น · 390 บาท
                 ➜
ล่าสุด:  สินค้า B + สินค้า C · 2 ชิ้น · 450 บาท

ใช้เวลาตัดสินใจ: 16 นาที
```

คีย์ข้อมูลที่รองรับ:

- `changed_from`

- `changed_to`

- `product_before`

- `product_after`

- `change_decision_minutes`

ถ้ายังไม่มีข้อมูล ให้ขึ้นว่า **ยังไม่พบประวัติเปลี่ยนสินค้า** ห้ามสร้างเรื่องขึ้นเอง

## 5. ระดับป้ายเตือน

### ระดับแดง: **กั้นก่อนส่ง**

ใช้เมื่อถ้าปล่อยต่ออาจเกิดความเสียหายจริง

ตัวอย่าง:

- โฟร์ยิงออเดอร์เดิมซ้ำ

- ยอดและสินค้าซ้ำกันหลายใบในช่วงเวลาสั้น

- ออเดอร์เดียวกันกำลังจะถูกส่งมากกว่าหนึ่งครั้ง

- สินค้าหรือยอดไม่ตรงกันแบบมีผลต่อเงิน

ปุ่มหลัก:

- **กั้นก่อนส่ง**

- **เปิด BLACKBOX ROOM**

- **ดูหลักฐาน**

### ระดับชมพู: **รอตัดสินใจ**

ใช้เมื่อมีความเป็นไปได้หลายทางและต้องอ่านหลักฐานเพิ่ม

ตัวอย่าง:

- ลูกค้าเปลี่ยนสินค้า

- ลูกค้าถามเฉยๆ แต่อาจถูกสรุปเป็นออเดอร์

- เบอร์ไม่ครบแต่ที่อยู่คล้ายประวัติเดิม

- ออเดอร์ก้อนกลางอาจถูกหยิบซ้ำ

ปุ่มหลัก:

- **เปิดเส้นทาง**

- **เทียบแชท**

- **ส่งให้คนตัดสิน**

### ระดับม่วง: **ข้อมูลพร่อง**

ใช้เมื่อยังทำงานต่อได้ แต่ควรตรวจให้ครบ

ตัวอย่าง:

- ไม่มีเบอร์เต็ม

- ชื่อไม่ครบ

- ไม่มีเวลาออเดอร์ชัดเจน

- สินค้ายังไม่แมป

ปุ่มหลัก:

- **เปิด ORDER CONTROL**

- **ดูข้อมูลที่ขาด**

### ระดับฟ้า: **แจ้งสถานะ**

ใช้สำหรับบอกเหตุการณ์ที่เกิดขึ้นแล้ว ไม่ได้แปลว่ามีปัญหา

ตัวอย่าง:

- Telegram ส่งสำเร็จ

- ออเดอร์ถูกส่งเข้าคิว

- ป้ายถูกปิดโดยผู้ตรวจ

- ระบบรับข้อมูลจาก n8n แล้ว

ปุ่มหลัก:

- **ดู Telegram Room**

- **ดูประวัติ**

## 6. ป้ายมาตรฐานที่ระบบควรใช้

ใช้คำสั้นๆ เหมือนป้ายในห้องควบคุม:

- **กั้นก่อนส่ง**

- **ซ้ำจากโฟร์**

- **ถามไม่ใช่สั่ง**

- **ลูกค้าเปลี่ยนของ**

- **เบอร์พร่อง**

- **ยอดกำลังซ้อน**

- **ก้อนกลางมีรอย**

- **สินค้าไม่ตรง**

- **ที่อยู่ต้องส่อง**

- **รอคนตัดสิน**

- **ส่งแล้ว**

- **ส่งไม่ออก**

- **ระบบเงียบผิดปกติ**

หนึ่งป้ายควรมีทั้ง **ชื่อสั้น** และ **คำอธิบาย** เช่น:

```
ป้าย: ซ้ำจากโฟร์
คำอธิบาย: payload เดิมเข้าระบบ 2 ครั้ง ห่างกัน 4 วินาที
ปลายทาง: BLACKBOX ROOM
การทำงาน: กั้นสำเนาไว้ก่อน ไม่ตัดสต็อกซ้ำ
```

## 7. เส้นทางส่งต่อของป้าย

```
เหตุการณ์เข้ามา
      ↓
BLACKBOX ALERT CENTER
      ↓
┌────────────────────────────────────────┐
│ ดูว่าเกิดอะไรขึ้น + ระดับ + หลักฐาน   │
└────────────────────────────────────────┘
      ↓
┌────────────────┬──────────────────┬─────────────────┐
│ ข้อมูลออเดอร์   │ ต้องแกะรอย       │ เรื่องการส่ง      │
│ ไม่ครบ/ต้องแก้  │ ซ้ำ/เปลี่ยน/บอท  │ คิว/ส่ง/ล้มเหลว    │
↓                ↓                  ↓
ORDER CONTROL    BLACKBOX ROOM      TELEGRAM ROOM
```

**กฎ:** ป้ายทุกใบต้องมีปลายทาง ไม่ปล่อยให้คนอ่านแล้วต้องเดาเองว่าจะไปต่อที่ไหน

## 8. หน้าหลักควรจัดวางอย่างไร

### ส่วนบน: สถานะห้อง

```
BLACKBOX ALERT CENTER
ห้องกำลังร้อน

03 กั้นก่อนส่ง · 07 รอตัดสินใจ · 12 เฝ้าดู · 00 ระบบหยุด
```

### ส่วนกลาง: ป้ายที่กำลังร้อน

เรียงตาม:

1. ระดับแดงก่อน

1. ความเสียหายที่อาจเกิด

1. เวลาที่ค้างอยู่

1. เวลาเกิดเหตุล่าสุด

### ฝั่งขวา: SIGNAL CONSOLE

แสดงภาพรวมแบบไฮเทค:

- จำนวนจุดร้อน

- ป้ายจาก n8n ล่าสุด

- ห้องปลายทางที่กำลังรับงานมากที่สุด

- สัญญาณระบบเงียบหรือไม่ตอบ

- HOT FEED 3–5 รายการล่าสุด

ฝั่งขวาเป็น **นาฟิกาและสัญญาณ** ไม่ใช่ตารางออเดอร์ซ้ำอีกชุด

### ด้านล่าง: ป้ายที่ปิดแล้ว

ปิดแล้วไม่ได้แปลว่าหาย ต้องย้อนดูได้:

- ใครปิด

- ปิดเพราะอะไร

- หลักฐานอะไรที่ใช้

- ส่งต่อไปห้องไหน

- ปิดเมื่อไหร่

## 9. ข้อมูลขั้นต่ำของป้ายหนึ่งใบ

ทุกป้ายควรมีข้อมูลอย่างน้อย:

```
alert_id             ตัวตนของป้าย
source_event_id      เหตุการณ์ต้นทาง
alert_type           ชนิดป้าย
severity             ระดับแดง/ชมพู/ม่วง/ฟ้า
headline             ชื่อสั้นบนป้าย
reason               เหตุผลแบบอ่านรู้เรื่อง
order_id             ออเดอร์ที่เกี่ยวข้อง ถ้ามี
page_name            เพจต้นทาง
customer_name        ลูกค้า ถ้ามี
order_time           วันที่และเวลา
product_before       สินค้ารอบแรก ถ้ามี
product_after        สินค้าล่าสุด ถ้ามี
cod_before           ยอดรอบแรก ถ้ามี
cod_after            ยอดล่าสุด ถ้ามี
decision_minutes     เวลาที่ใช้ตัดสินใจ ถ้ามี
destination_room     ห้องปลายทาง
status               สถานะป้าย
created_at           เวลาเกิดป้าย
closed_at            เวลาปิดป้าย
closed_by            ผู้ปิดป้าย
```

หลักสำคัญคือ **ไม่ต้องมีข้อมูลครบทุกช่องจึงจะสร้างป้ายได้** ข้อมูลที่ขาดให้ติดป้ายว่า “ข้อมูลพร่อง” แทนการทิ้งเหตุการณ์

## 10. กติกาไม่ให้ป้ายเตือนกลายเป็นเสียงรบกวน

- เหตุการณ์เดียวกันต้องรวมเป็นป้ายเดียว แต่เก็บหลักฐานย่อยไว้ข้างใน

- ป้ายซ้ำจาก retry ของระบบต้องไม่ยิงเตือนซ้ำทุกครั้ง

- ป้ายที่คนปิดแล้วต้องไม่เด้งกลับโดยไม่มีเหตุการณ์ใหม่

- ถ้าคนกดว่า “ไม่ใช่ปัญหา” ต้องเก็บคำตอบไว้ปรับกติกา

- ถ้าไม่มีภัยแดง ให้แสดงว่า **ระบบกำลังเฝ้าอะไรอยู่** แทนการโชว์เลข 0 โล่งๆ

- การเตือนทุกใบต้องบอกปลายทาง ไม่ใช่แค่บอกว่าพบปัญหา

## 11. Definition of Done ของส่วนห้องเตือน

ถือว่าส่วนนี้ใช้งานได้เมื่อ:

- [ ] มีหน้า **BLACKBOX ALERT CENTER** แยกชัดจากสามห้องปลายทาง

- [ ] ทุกป้ายมีระดับ, เหตุผล, หลักฐาน และปลายทาง

- [ ] มีคอลัมน์เพจ, Order, วันที่, เวลา, สินค้า และ COD

- [ ] รองรับการแสดง `สินค้าเดิม → สินค้าใหม่`

- [ ] รองรับเวลาที่ใช้ตัดสินใจเปลี่ยนสินค้า

- [ ] เบอร์ไม่ครบยังสร้างป้ายได้

- [ ] ข้อมูลจาก n8n ไม่ถูกลบหรือเขียนทับ

- [ ] กดจากป้ายไปห้องปลายทางได้

- [ ] ปิดป้ายแล้วมีรอยมือและย้อนดูได้

- [ ] ไม่มีข้อมูลก็ยังแสดงสถานะการเฝ้าระวัง

- [ ] Alert Center ไม่กลายเป็นหน้าจัดการออเดอร์ซ้ำกับห้องอื่น

> **สี่ห้องมีหน้าที่คนละอย่าง แต่ห้องเตือนเป็นจุดที่มองเห็นทั้งระบบก่อนคนอื่น**
