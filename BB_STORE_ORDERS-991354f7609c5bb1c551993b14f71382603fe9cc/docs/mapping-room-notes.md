# บันทึกข้อกำหนดห้องแมปสินค้า

สถานะเอกสาร: **รอสรุปก่อนพัฒนาเว็บและก่อนสร้างตารางจริง**

## หลักการสำคัญ

ห้องนี้ยังไม่อนุญาตให้เขียนทับข้อมูลใน `product_master` และยังไม่ให้แก้ข้อมูลใน `product_map_master` จนกว่าจะสรุป schema และกระบวนการใช้งานร่วมกันเรียบร้อยแล้ว

## `product_aliases`

`product_aliases` ต้องรองรับคำดิบของสินค้าได้หลายรูปแบบ เพราะสินค้าหนึ่งรายการอาจมีคำเรียกหลายแบบ คำสะกดผิดหลายแบบ หรือข้อความจากหน้าบ้านหลายรูปแบบ การอ่านข้อมูลจึงห้ามเลือกดึงหรือแสดงเพียงค่า alias ช่องเดียวแล้วถือว่าเป็นข้อมูลทั้งหมด

ข้อกำหนดเบื้องต้น:

- ต้องอ่าน alias/คำดิบทุกค่าที่ผูกกับสินค้าเดียวกัน
- ต้องรองรับหลายแถวต่อหนึ่ง SKU หรือหลายรูปแบบในฟิลด์เดียว หาก schema ใช้รูปแบบนั้น
- ต้องไม่ตัดคำดิบทิ้งระหว่างการแสดงผลหรือส่งเข้า Alien Review
- การ normalize คำมีไว้ช่วยค้นหาและจับคู่เท่านั้น ต้องเก็บค่าดิบต้นฉบับไว้ครบ
- ยังไม่สรุปว่าจะใช้ชื่อคอลัมน์ใดเป็น canonical จนกว่าจะตรวจ schema จริงของฐานข้อมูล
- ยังไม่สร้างตารางหรือเขียน migration ในรอบนี้

## `product_map_master`

`product_map_master` มีการทำแมปไว้อยู่แล้ว ระบบไม่ต้องสร้างแมปใหม่และไม่ต้องแก้ไขข้อมูลในห้องนี้ในรอบแรก ให้ทำเพียงอ่านข้อมูลให้ถูกต้องเพื่อใช้ประกอบการแสดงผลและการแพ็กสินค้า

ข้อกำหนดเบื้องต้น:

- อ่าน SKU และข้อมูลแมปที่มีอยู่แล้ว
- อ่านชื่อมาตรฐานและ `master_display_for_packer` จากแหล่งที่กำหนด
- อ่านจำนวน/quantity ที่มีอยู่ตาม schema จริง โดยไม่เดาคอลัมน์
- ไม่ insert, update, upsert หรือ delete ใน `product_map_master`
- ไม่ใช้ข้อมูลจาก `product_map_master` ไปเขียนทับ `product_master`
- ถ้าจับคู่ไม่ได้ ให้ส่งคำดิบครบทั้งก้อนเข้า Alien Review เพื่อรอตรวจ ไม่ตัดเหลือคำเดียว

## ลำดับการทำงานที่ต้องยึด

1. อ่านออเดอร์จากตารางต้นทางของค่าย เช่น `bb_orders`
2. เก็บข้อความสินค้าและคำดิบทุกฟิลด์ไว้ครบ
3. อ่าน alias ทั้งหมดจาก `product_aliases` เมื่อ schema ได้ข้อสรุปแล้ว
4. อ่านแมปที่มีอยู่แล้วจาก `product_map_master`
5. อ่านชื่อมาตรฐาน/`master_display_for_packer` จาก `product_master` แบบ read-only
6. เติมจำนวนจากข้อมูลที่อ่านได้
7. ถ้าแมปสำเร็จ จึงแสดงผลพร้อมแพ็ก
8. ถ้าแมปไม่สำเร็จ ส่งคำดิบครบถ้วนเข้า Alien Review

## สิ่งที่ยังไม่ทำ

- ยังไม่สร้างตารางจริง
- ยังไม่สร้าง migration
- ยังไม่เขียนหน้าเว็บใหม่
- ยังไม่สรุป schema ของ `product_aliases`
- ยังไม่สรุปว่าการเก็บหลาย alias จะเป็นหลายแถวหรือหลายค่าในฟิลด์เดียว
- ยังไม่เขียนข้อมูลกลับ `product_master` หรือ `product_map_master`

## ข้อแก้ไขสำคัญ: `master_display_for_packer` เป็นค่าผลแมปสำเร็จรูป

`master_display_for_packer` ไม่ใช่ฟิลด์ที่ n8n หรือหน้าเว็บต้องสร้างขึ้นใหม่ แต่เป็นคอลัมน์สำเร็จรูปที่ระบบแมปเดิมจัดเตรียมไว้แล้ว ตัวอย่างเช่น:

```text
🟩 MOND_GREEN(ม่อนเขียว)ปี้ๆๆ 1 คอต
```

คำกวน/คำเฉพาะที่ผู้ใช้ตั้งใจใส่ไว้ในข้อความนี้เป็นส่วนหนึ่งของผลแมปจริง ห้าม normalize ห้ามตัด ห้ามเปลี่ยนคำ และห้ามประกอบข้อความใหม่จาก `sku`, `product_name`, `th_name`, `quantity` หรือฟิลด์อื่น

ลำดับที่ถูกต้อง:

```text
n8n อ่านคำดิบ
  ↓
ค้น alias / คำย่อ / สี / แบรนด์
  ↓
หา SKU และ product_id
  ↓
ตรวจ product_master แบบอ่านอย่างเดียว
  ↓
ใช้ค่า master_display_for_packer ที่มีอยู่แล้ว
  ↓
vw_*
  ↓
หน้าเว็บอ่าน master_display_for_packer เท่านั้น
```

กติกาสำหรับหน้าเว็บ:

- แสดงชื่อสินค้าหลักจาก `master_display_for_packer` เท่านั้น
- ไม่ fallback ไปสร้างชื่อจาก `display_for_packer`, `final_display_for_packer`, `product_name`, `th_name` หรือ `sku`
- ถ้า `master_display_for_packer` ว่าง ให้แสดงว่า `ยังไม่มี Master Display` และส่งเข้าตรวจ ไม่เดาข้อความแทน
- ใช้ `mapping_status`, `sku`, `product_id`, `source_logic` เป็นข้อมูลตรวจสอบเบื้องหลังเท่านั้น
- เก็บและแสดงคำดิบแยกต่างหากได้ แต่ห้ามนำคำดิบมาปนหรือทับ Master Display
- ห้ามแก้ไขหรือเขียนทับ `product_master`, `product_map_master`, และค่าของ `master_display_for_packer`

ข้อสรุป: ระบบแมปเดิมเป็นผู้กำหนด Master Display; n8n/View เป็นผู้ส่งต่อ; เว็บเป็นผู้อ่านและแสดงผลเท่านั้น

## Identity กลางที่ทุกห้องต้องใช้ร่วมกัน

ข้อมูลจาก n8n ที่ต้องติดตามร่วมกันทุกห้อง ได้แก่:

```text
upsert_key
facebook_name
threadId
thread_id
page_name
order_time_display
order_number
customer_id
chattime
```

กติกาการใช้:

- `upsert_key` ใช้เป็นคีย์อ้างอิงออเดอร์/รายการจาก n8n
- `facebook_name` ใช้เก็บชื่อบัญชีหรือชื่อผู้สั่งจาก Facebook ตามข้อมูลต้นทาง
- `thread_id` เป็นชื่อ canonical สำหรับห้องแชท
- `threadId` เป็นชื่อจาก payload เดิม/legacy และต้องเก็บไว้เพื่อไม่ให้ข้อมูลหาย แต่ระบบภายในควร normalize มาใช้ `thread_id`
- `page_name` ระบุเพจต้นทาง
- `order_time_display` ใช้แสดงเวลาตามรูปแบบที่ n8n จัดเตรียมไว้
- `order_number` ใช้เชื่อมออเดอร์กับห้องส่งและประวัติ
- `customer_id` ใช้ระบุตัวลูกค้าจากระบบต้นทาง
- `chattime` ใช้เก็บเวลาจากแชท/เหตุการณ์ต้นทางตาม payload เดิม

ทุกห้องที่อ่านข้อมูล เช่น Alien Map, ห้องส่ง, Inventory, Alias และ Order View ต้องอ้างอิง identity ชุดเดียวกัน ไม่สร้างชื่อฟิลด์คนละแบบ และต้องรักษาค่าต้นฉบับจาก n8n ไว้ครบ

## Identity กลางฉบับแก้ไขล่าสุด

ชุดฟิลด์มาตรฐานที่ทุกห้องต้องใช้ร่วมกันคือ:

```text
upsert_key
facebook_name
thread_id
page_id
page_name
order_time_display
order_number
customer_id
chattime
```

กติกา:

- `upsert_key` คีย์อ้างอิงรายการจาก n8n
- `facebook_name` ชื่อบัญชี/ชื่อผู้สั่งจาก Facebook
- `thread_id` รหัสห้องแชทหลัก ใช้เป็น canonical field
- `page_id` รหัสเพจต้นทาง
- `page_name` ชื่อเพจต้นทาง
- `order_time_display` เวลาที่ใช้แสดงผลจาก n8n
- `order_number` เลขออเดอร์กลาง
- `customer_id` รหัสลูกค้าจากต้นทาง
- `chattime` เวลาเหตุการณ์จากแชท

`threadId` ไม่อยู่ในชุด canonical ล่าสุด หาก payload จาก n8n ยังส่งมา ให้รับไว้เป็น legacy input แล้ว normalize เข้า `thread_id` โดยไม่ใช้เป็นชื่อฟิลด์หลักในระบบใหม่

## Identity กลางฉบับล่าสุดเพิ่มเติม

เพิ่มฟิลด์จำนวนเงินเก็บปลายทาง:

```text
upsert_key
facebook_name
thread_id
page_id
page_name
order_time_display
order_number
customer_id
cod
chattime
```

`cod` ใช้เก็บยอดเก็บเงินปลายทางของออเดอร์จากข้อมูลต้นทาง/n8n และทุกห้องต้องอ้างอิงค่าเดียวกัน โดยไม่คำนวณหรือสร้างยอดใหม่เอง เว้นแต่เป็นการตรวจสอบความถูกต้องที่แสดงเป็นสถานะแยกต่างหาก

## กติกาหลักฐานเมื่อข้อมูลขัดแย้ง: เชื่อ `raw_text`

เมื่อ `raw_text` ขัดแย้งกับ `final_display_for_packer`, `display_for_packer`, จำนวน หรือผลแมปที่ระบบส่งออกมา ให้ถือ `raw_text` เป็นหลักฐานต้นทางสูงสุด

ตัวอย่าง:

```text
raw_text:
🟢CAVALLO_GREEN | 2 คอต

final_display_for_packer:
🟩 MOND_GREEN(ม่อนเขียว) 1 คอต
```

กรณีนี้ต้องสรุปว่า:

- คำสั่งจริงจากต้นทางระบุ `CAVALLO_GREEN`
- จำนวนจริงตามคำสั่งต้นทางคือ `2 คอต`
- `final_display_for_packer` ที่เป็น `MOND_GREEN 1 คอต` เป็นผลที่ขัดแย้งและห้ามใช้ทับ raw
- ห้ามถือว่ารายการนี้แมปสำเร็จเพียงเพราะมี SKU หรือ final display
- ต้องส่งเข้า Alien Review ด้วยสถานะอย่างน้อย `RAW_RESULT_CONFLICT` และ `QUANTITY_MISMATCH`
- ถ้า `master_display_for_packer` เป็น null ยิ่งห้ามสร้างข้อความทดแทน

ลำดับความน่าเชื่อถือของข้อมูล:

```text
raw_text จากต้นทาง
  > หลักฐานข้อความ/แชทต้นฉบับ
  > alias ที่ตรวจสอบย้อนกลับได้
  > ผลแมปจาก n8n
  > final_display_for_packer / display_for_packer ที่อาจถูกประกอบผิด
```

หน้าเว็บต้องแสดง raw แยกจากผลระบบอย่างชัดเจน และต้องไม่ใช้ผลปลายทางที่ขัดแย้งมาแก้ไขหรือลบ raw เด็ดขาด
